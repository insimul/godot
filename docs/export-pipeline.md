# The export pipeline, generated types, and releasing

This page is for **contributors** and for anyone working on the Insimul platform's game-export
flow — not for a developer simply dropping the addon into their own project. It covers three
internal concerns: the game-template tree the platform copies into exported games, where the
plugin's GDScript types come from, and how a release is staged.

## The game-template tree

Everything under [`../templates/`](../templates/) is a **game-template tree**. When a creator
exports a world for Godot, the Insimul platform's export pipeline copies this tree **verbatim**
into a fresh Godot project, then substitutes `{{UPPER_SNAKE_CASE}}` placeholder tokens in the text
files with values derived from the exported world (world name, genre, counts, palette colors,
player/combat tuning, and so on).

- **The contract is machine-checked.** [`../templates/TEMPLATE_MANIFEST.json`](../templates/TEMPLATE_MANIFEST.json)
  is the authoritative list of every file the pipeline copies and the exact set of placeholders
  each file bears. A drift guard fails if the manifest and the tree disagree, if a
  placeholder-bearing file is unlisted, or if any template file reaches into another engine's
  package.
- **Placeholder syntax:** `{{TOKEN}}` where `TOKEN` is upper snake case — e.g. `{{WORLD_NAME}}`,
  `{{TERRAIN_SIZE}}`, `{{ROAD_COLOR_R}}`. The manifest's top-level `placeholders` array is the
  full set this package uses.
- **Dependency rule:** template files depend only on (a) this package, (b) generated code, and
  (c) exported world-data JSON — never on a sibling engine's package. The guard enforces that
  no-cross-engine-reach-in rule.

## Where the GDScript types come from

The plugin's types fall into three tiers. **Only the *generated* tier is derived from the
canonical Insimul core schemas** — the others are hand-maintained and stay that way.

| Tier | Files | Source of truth | Editable? |
| --- | --- | --- | --- |
| **Generated** | `addons/insimul/generated/{InsimulSaveFile,InsimulSaveFileEnvelope,InsimulWorldIR}.gd` — Godot 4 `class_name` DTOs with `from_dict`/`to_dict` | The core save-file / save-envelope / world-IR JSON schemas | **No** — regenerated by codegen, drift-guarded |
| **Hand-written (SDK)** | `addons/insimul/insimul_types.gd`, `insimul_world_export.gd`, and the addon runtime (`insimul_client.gd`, `insimul_npc.gd`, `insimul_http_client.gd`, `insimul_local_provider.gd`, audio/mic/lipsync) | Hand-maintained (engine-facing / proto-derived) | **Yes** |
| **Template-legacy** | `templates/scripts/**/*.gd` (e.g. `systems/save_system.gd`, `core/data_loader.gd`, the world generators) — game-side scripts vendored into exported games | Hand-maintained | Being retired by the per-engine runtime work |

**Why nothing in the addon was migrated to the generated classes:** no live addon type duplicates
a generated schema DTO. `insimul_world_export.gd` parses the *distilled offline export* (a
flattened dialogue-context shape), **not** the full world IR, so it stays hand-written. New
save/world-IR code should parse into the generated classes and read fields off them — see the
boundary convention in `addons/insimul/generated/README.md`.

## Releasing to the Godot Asset Library

The addon is published to the Godot Asset Library (metadata in
[`../asset-lib.json`](../asset-lib.json)). To stage a release build:

```sh
node scripts/release/build-assetlib-zip.mjs
```

This stages `addons/insimul/**` (plus docs, excluding `templates/`) into `dist/insimul-godot/`,
zips it to `dist/insimul-godot-<version>.zip` in Asset Library layout, and asserts the file set.
It does **not** publish. The package version is a single source of truth shared across
`plugin.cfg`, `asset-lib.json`, and the platform's version manifest, and the mismatch is enforced
by a manifest check — bump them together.
